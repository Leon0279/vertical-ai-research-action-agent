# Agent Loop 最小评测基线

## 1. 目的

这份文档用于回答一个具体问题：Agent Loop 的下一次重构，是否在不降低回答质量的前提下，提高了研究效率。

当前实现记为 **V1**，待评估的新实现记为 **V2**。每次重构后，使用相同的五个问题、相同的项目上下文和相同的人工评分标准重新运行，并填写对应的 V2 数据。

本基线同时观察两个维度：

- **回答质量**：回答是否正确、完整、可执行，引用和不确定性表达是否合格。
- **运行效率**：耗时、迭代、检索、Evidence Processing 和 Memory 是否产生了与成本相称的增益。

速度变快但质量下降，不算改进；质量相同但减少无效迭代、外部调用或同步写回延迟，才算有效优化。

## 2. 使用方式

1. 使用对应 Case 的固定问题和约定上下文调用 `POST /v1/agent/run`。
2. 保存公开响应、HTTP 状态和 `trace_id`，从 `logs/app.jsonl` 汇总本节定义的客观指标。
3. 按统一 rubric 对公开响应进行人工评分，并写明扣分理由。
4. 将结果填入该 Case 的 V1 或 V2 列；比较质量、效率和失败模式，不要求两次运行具有完全相同的工具轨迹。

评测记录不得复制内部 LLM prompt、Memory 正文、API Key、用户 ID、Session ID 或 Project ID。评测问题本身不是内部 prompt，可以原文保留以确保回归输入一致。

## 3. 统一人工评分

每项 `0–2` 分，总分 `10` 分。必须同时记录各项理由，不能只填写总分。

| 维度 | 0 分 | 1 分 | 2 分 |
|---|---|---|---|
| 正确性 | 存在关键事实错误，或结论与证据明显冲突 | 核心方向基本正确，但有未充分支撑、容易误导或边界不清的内容 | 核心事实和推理正确，结论与现有证据一致 |
| 任务完成度 | 未回答主要问题 | 回答了部分任务，仍遗漏重要要求 | 直接且完整地完成用户请求 |
| 可执行性 | 没有可采取的下一步 | 有建议，但缺少顺序、条件或足够具体的动作 | 给出清晰、现实且可以立即执行的下一步 |
| 引用质量 | 无引用，或引用无法支撑主要结论 | 有可核验引用，但权威性、覆盖度或结论对应关系不足 | 关键结论均由相关、可靠且可核验的来源支撑 |
| 不确定性表达 | 把未知、假设或弱证据表述为确定事实 | 提及部分限制，但仍有重要假设未披露 | 明确区分事实、推断和假设，并说明关键限制 |

## 4. 统一客观指标

| 指标 | 口径 |
|---|---|
| HTTP 状态 | 前端实际收到的 HTTP 状态；若网关超时但后端继续完成，两个结果都要记录 |
| research status | `agent_run_completed.research_status` |
| 总耗时 | `agent_run_completed.duration_ms` |
| 研究轮数 | `agent_run_completed.research_iteration_count` |
| retrieval family 顺序 | 按 iteration 排列每轮实际使用的 retrieval family |
| meaningful / limited / no-gain 轮数 | 按 `research_iteration_outcome.evidence_gain` 统计 |
| 候选材料数 | 各轮 `evidence_processing_completed.candidate_material_count` 之和，并区分 Memory 与 External |
| 保留 Evidence 数 | 各轮 `processed_evidence_count` 之和；它不是最终引用数 |
| 丢弃材料数 | 各轮 `dropped_material_count` 之和 |
| Memory 查询次数及 utility | `research_retrieval_history_updated` 中 Memory family 的次数和 `result_utility` |
| 外部检索次数 | Docs、Web、Paper 等非 Memory retrieval attempt 数量 |
| 最终引用数 | 输出阶段或 `agent_run_completed.citation_count`，不使用中间研究阶段的累计引用数代替 |
| Memory 写回 | `memory_writeback_completed` 的耗时、written、no-write 和 failed 数量 |
| 关键失败标签 | 对日志事实的人工归因；必须在 Case 中解释，不得当成原始日志字段 |

“有效轮数”在对比表中统一指 `meaningful_gain` 轮数。`limited_gain` 单独保留，不与完全无增益混为一谈。

## 5. 固定评测问题

### Case 1：项目化推荐

**固定问题**

> 作为一个 AI 应用开发工程师，学习强化学习的第一步是什么？

**评测重点**

- 是否结合项目背景给出面向 AI 应用开发的推荐，而不是泛化学习清单。
- 是否使用足以支撑推荐的外部证据。
- Memory 是否减少重复研究，而不是重复占用研究轮次。
- 在已经能回答时是否及时停止。

**预期行为**

- 可以先读取 Memory，但低价值或重复内容不应持续占用轮次。
- 推荐应说明“为什么这是第一步”以及一个可以立即执行的动作。
- 不规定必须选择哪一种外部工具，但无关来源不应被反复使用。

## 6. V1/V2 判定原则

V2 至少应满足以下条件，才能认为重构有效：

1. 人工总分不低于 V1；任一质量项下降时必须解释取舍。
2. 关键事实和主要建议仍有足够证据，不能通过删掉研究步骤来掩盖质量下降。
3. 总耗时、无增益轮数、无效工具调用或同步非关键路径耗时至少有一项显著下降。
4. Memory 命中必须产生可观察的成本降低或质量提升；否则只算额外开销。
5. 对信息不足的任务，正确澄清或明确假设优于增加检索轮次。

五个 Case 不要求使用相同工具序列，也不以“跑满 iteration budget”为成功。Agent 应根据任务复杂度、已有上下文和新增证据决定是否继续。

## 7. 当前覆盖范围

- 当前采用人工评分和人工日志汇总，不包含自动评测脚本。
- Case 1 已填写 V1；Case 2–5 等实际运行后再填写，避免用推测数据制造基线。
- 本文档只评估 Agent Loop，不修改运行时逻辑、HTTP API、Memory、数据库或日志行为。
